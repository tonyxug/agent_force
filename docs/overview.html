agent_force

A small Bash framework: you talk to one Claude Code leader. The leader gives your tasks to Claude Code workers, watches them in the background, and reports results and questions back to you. Every agent runs in its own tmux session on a private socket.

1. Architecture

There is no daemon and no server program. The leader is a normal Claude Code session; its "behavior" is prompts/leader.md plus the helper scripts on its PATH. All sessions share one tmux server on socket agent_force.

The leader never touches tmux directly; it calls af-* helpers. The helpers talk to worker panes only through tmux I/O (paste text in, capture the screen out).

2. Task workflow

One task from your ask to the leader's report. The leader never blocks: after it sends a task, it starts a background watch and returns to you at once.

Several workers can run this loop at the same time. The leader runs one background af-watch per task it sends.

3. Who talks to whom (one task)

The background af-watch exits when the task ends. Claude Code wakes the leader when a background command finishes, so no polling happens in your chat.

4. Worker status machine

Each agent has one status word in agents/agent_NN/status. af-watch and af-status update it with af_check.

done, failed, blocked, lost and interrupted are all "turn ended" states; the next af-send moves the worker back to working. lost means the task tag scrolled out of the pane for 10 polls in a row (about 5 minutes), so the outcome is unknown.

5. How status is read from the screen

No hooks, no APIs. The worker's system prompt (prompts/worker.md) tells it to end every answer with one marker line. af-send types a unique tag after each task. af-parse counts only markers that sit alone on a line below the last tag line, so old answers and quoted markers do not count.

❯ [Pasted text #1 +12 lines] (task agent_02-001)     ← last tag line: parsing starts below it

⏺ I wrote the briefing. Sources: …
  …
⏺ [agent_02: done]                                   ← marker alone on its line → state "done"

❯

The tag is typed with send-keys -l after a bracketed paste, so it stays visible even when Claude collapses a long paste to [Pasted text #1 +N lines]. The tmux history limit is 100000 lines, so the tag stays reachable for long answers.

6. CLI lifecycle

CommandWhat it does
agent_force startStarts a new leader agent_01 in the current folder, without attaching. Only one leader per machine.
agent_force start --latestResumes the last leader chat and every worker that is not closed.
agent_force stopKills all agents. Keeps state and worktrees.
agent_force listOne line per live agent: name, role, status, folder, branch, last task.
agent_force connect NAttaches to agent_0N. 1 is the leader. Detach with Ctrl-b d.

9. Key design choices

Screen, not hooksStatus comes only from tmux capture-pane plus marker lines. Works with any agent CLI that can print a line.
Non-blocking leaderEach send starts one background af-watch. Claude Code wakes the leader when it exits.
Private tmux sockettmux -L agent_force keeps agent sessions apart from your own tmux.
Worktree only for codeTasks that change the repo get an isolated worktree and branch. Nothing is committed, merged or pushed without you.
Workers persistSessions stay open after a task, so follow-ups go to the same chat. start --latest resumes them.
Adapter seamOnly adapters/claude/ knows Claude. A new agent type needs its own launch.sh and ready.sh.
Portable BashBash 3.2 compatible, macOS and Linux. Needs tmux ≥ 3.2, git, jq, uuidgen.
Full permissionsLeader and workers run with --dangerously-skip-permissions, so they never stop on a permission prompt.
